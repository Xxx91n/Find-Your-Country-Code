## 2. 四问结论与推荐

### Q3 → D-008：CI 闭环形态

**调研结论**：单人仓库也走 trunk-based + 短命分支 + PR 门禁 + **squash merge**；**权威验收锚点是 main 上的绿 run**（PR 上的 run 只证明候选）；`push ≠ 落地`。
**推荐**：① 授权 push 后**分支 run 作增量确认**；② 合入 main 后取 **main 上的 run 作闭环证据**（run ID 入账）；③ main 分支保护（禁 force-push/删除 + Require status checks，job 名唯一）；④ 只开 squash merge；⑤ 验收口径一句话 `PR #N + checks 绿 + main commit <sha> + Release run <id>`。
**负向**：不得把分支 run 当闭环证据；**不开 Require approvals**（自审自批/admin 死锁）；**不引入 merge queue**。

### Q5 → D-009：门槛②的可测化

**调研结论**：站点级 FPR 是稀有二项事件，**抽样量应由「CI 上界 < 门槛」反推，而非点估计**。
**推荐**：① 1‰ 门槛 + 95% CI 上界 < 门槛 ⇒ **n ≥ 3000 良性站点零误报**（rule of three `3/n`；< 0.5‰ 则 6000）；② **分层 + Neyman 配额**，每层正例期望 ≥ 5 才用分层 Wilson；③ 判定用 **OC 双点**（AQL 0.5‰ / α=5%；LTPD 2‰ / β=10%）反解 (n,c)；④ 运行期用**燃烧率渐进处置**（>3× 阻断发版 / >1× 冻结并扩样 / <0.5× 常态）；⑤ 门槛收窄至 **`tier ∈ {auto}`**，`lowkey` 只监控；⑥ 配 **FP/FN 双指标 + 一键上报率 + reviewer agreement ≥90%**；⑦ **先行 pilot ~500 站点**估层内方差。
**负向**：不得用**点估计**；不得用**正态近似 CI**（1e-3 量级下覆盖度差）；不得用 **Clopper-Pearson**（过保守，多花 10–20% 样本）；不得把 FP 率单独设为 KPI。

> **口径对接（关键）**：调研的「阻断发版」**落在已有 ADR-0010 发布门**，**不触碰 ADR-0008 决策 1** 的「真实站点层永不进 `pull_request`」——两者不矛盾。

### Q6 → D-010：GF sync 的确认责任人与时点

**调研结论**：分发平台**无审核门**（同步即发布）；确认责任 **100% 在作者**；业界把确认门**前移到仓库侧**——同步源只跟 **release 分支/tag**、以 **`@version` 变更**为唯一发布门。
**推荐**：① 确认人 = 能向 release 分支（或 tag）合并代码的人；② 时点 = `@version` 变更；③ 留痕三层（Git tag/changelog · CI run/可选 environment required reviewers · 平台版本历史）；④ 红线：**绝不让自动同步跟随「维护权可能易手的上游」**（The Great Suspender 教训：200 万用户中招）。
**负向**：不得据此放宽 **Cycle-7 D-002 负向**（禁 CI 主动写 GF、禁伪造 session cookie 的推送 hack、禁据此宣布弃用 GF）；**确认前仍不得声称 D-002 送达链已闭合**。

### Q7 → D-011：交付单位

**调研结论**：业界**没有「唯一正确节奏」**，但高度收敛——**每个变更保持可发布、按固定节奏/积累阈值批量对外发版，安全与严重 bug 的 patch 随时插发不排队**；纯「每 commit 即发」与「攒很久才爆发」两端均被批评。
**推荐**：① **固定节奏（双周/月度）人工收割一版**；② 每 PR 附 **changeset 意图文件**；③ **安全 patch 豁免**（不排队）；④ breaking 只进批量点 + 迁移指南；⑤ 每个发布点打 tag。
**关键判据（对本仓）**：GF 用户自动更新 = **外部无法协同升级的下游** ⇒ 必须**严格 SemVer + 意图积累式批量**，**禁止全自动 patch 直发**。
**负向**：不得「每 commit 即发」（版本噪音；npm 生态 **44% breaking 藏在 minor/patch**）；不得「攒很久才爆发」；breaking **永不藏进 patch**。

## 5. 辩证性说明（对调研的自我修正与局限）

调研结论**未被全盘采纳**，以下四点已如实记录：

1. **两处结论属于“业界已判定的非银弹”**：DORA 的 trunk-based 结论是**相关性非因果**（gitflow.dev 明确 caveat）；实证研究的“发布频率↔市场份额”是**曲线关系**（过频反噬），且**拐点无量化阈值**（PACIS 2013 全文被 403 拦截）。
2. **“每千站点”在业界没有同名标准**：调研自述这是**四个成熟领域的组合方案**，站点级是否等同“每事件”框架取决于注入机会次数 ⇒ **D-009 属外推，不是现成标准**。
3. **调研自身承认的缺口**：dora.dev 原文超时未读（Q3）· Neyman 方差先验需自测（Q5）· OpenUserJS 同步细节仅二手、SLSA 三级+ 对个人作者超配（Q6）· npm 数据能否外推到其他生态未验证（Q7）。
4. **对“站内人工确认”的替代不等同于原残留失效**：Q6 调研取代的是**控制点选型**；原残留的结论（**确认前不得声称送达链闭合**）**仍然有效**。
